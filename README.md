# course-events-aggregator

Сервис-агрегатор мероприятий: синхронизирует события из Events Provider, обслуживает
регистрацию на мероприятия и доставляет уведомления о покупке билетов через
Transactional Outbox.

## Разработка

Настройка окружения:

```bash
uv sync --dev
uv run pre-commit install
```

Хуки прогоняются автоматически при `git commit`. Прогнать вручную на всех файлах:

```bash
uv run pre-commit run --all-files
```

Миграции:

```bash
uv run alembic upgrade head
uv run alembic revision --autogenerate -m "описание изменения"
```

Запуск локально:

```bash
uv run uvicorn src.main:app --reload
```

Swagger доступен на `http://localhost:8000/docs`.

Секретов в коде нет.

|----------------------------------------|-------------|--------------|----------------------------------------------------------------------------|

| `EVENTS_PROVIDER_BASE_URL`             | да          | —            | Базовый URL Events Provider                                                |
| `EVENTS_PROVIDER_API_KEY`              | да          | —            | API-ключ Events Provider                                                   |
| `CAPASHINO_BASE_URL`                   | да          | —            | Базовый URL Notification-сервиса                                           |

## Запуск фоновых процессов

Отдельных процессов или контейнеров не требуется: обе фоновые задачи запускаются
корутинами в `lifespan` приложения (`src/main.py`) и живут столько же, сколько процесс
uvicorn.

- **Синхронизация событий** — периодически опрашивает Events Provider по курсору
  `changed_at` и обновляет локальную таблицу `events`. Итог каждого прогона пишется в
  таблицу `sync_meta` (поле `sync_status`): `never_run` — синхронизация ещё не
  запускалась, `ok` — последний прогон завершился успешно, `error` — прогон упал с
  исключением (оно логируется через `logger.exception` и пробрасывается дальше, а в
  `sync_meta` фиксируются статус `error` и время попытки). Текущее состояние отдаёт
  `GET /api/sync/status`.
- **Outbox-воркер** — читает неотправленные записи из таблицы `outbox` и доставляет
  уведомления в Capashino.

При остановке приложения обе задачи отменяются и дожидаются завершения текущей итерации.

## API

### `GET /api/events`

Список синхронизированных событий с пагинацией.

Query-параметры: `date_from` (по умолчанию `2000-01-01`), `page` (≥ 1, по умолчанию `1`),
`page_size` (1–100, по умолчанию `20`).

### `GET /api/events/{event_id}`

Детали события. `404` — событие не найдено.

### `GET /api/events/{event_id}/seats`

Свободные места события.

| Код | Причина |
|---|---|
| `200` | Список свободных мест |
| `400` | Событие недоступно для регистрации |
| `404` | Событие не найдено |
| `409` | Статус события изменился с последней синхронизации |

### `POST /api/tickets`

Регистрация на мероприятие (покупка билета).

Тело запроса:

```json
{
  "event_id": "0fd1c941-bf49-4290-a88e-5f5de906577d",
  "first_name": "Ivan",
  "last_name": "Ivanov",
  "email": "ivan@example.com",
  "seat": "A1",
  "idempotency_key": "8f14e45f-ea6a-4f2b-9d3a-1c2e5b7a9d40"
}
```

| Поле | Обязательно | Описание |
|---|---|---|
| `event_id` | да | UUID события |
| `first_name` | да | Имя |
| `last_name` | да | Фамилия |
| `email` | да | Email, валидируется |
| `seat` | да | Место, должно соответствовать схеме зала |
| `idempotency_key` | нет | Ключ идемпотентности, строка до 255 символов |

Успешный ответ — `201`:

```json
{ "ticket_id": "30213bac-4fbd-43e6-b558-0b7061323302" }
```

Коды ошибок:

| Код   | `detail`                                                | Причина                                                |
|-------|---------------------------------------------------------|--------------------------------------------------------|
| `400` | текст ошибки                                            | Событие недоступно для регистрации                     |
| `400` | `Seat does not exist for this venue`                    | Место не соответствует схеме зала                      |
| `400` | текст ошибки                                            | Место уже занято                                       |
| `404` | `Event not found`                                       | Событие не найдено                                     |
| `409` | `Event status changed since last sync, try again later` | Статус события изменился с последней синхронизации     |
| `409` | `Idempotency key was used with different request data`  | Ключ идемпотентности переиспользован с другими данными |
| `422` | —                                                       | Тело запроса не прошло валидацию                       |

### `DELETE /api/tickets/{ticket_id}`

Отмена регистрации. `200` — `{"success": true}`, `404` — билет не найден.

Идемпотентность для отмены не поддерживается.

### `POST /api/sync/trigger`

Ручной запуск синхронизации событий. Используется для отладки и в автотестах.

### `GET /api/sync/status`

Состояние последней синхронизации событий из таблицы `sync_meta`.

```json
{
  "status": "ok",
  "last_sync_time": "2026-09-09T05:53:28.123456+00:00",
  "last_changed_at": "2026-09-08T21:00:00+00:00"
}
```

| Поле | Описание |
|---|---|
| `status` | `never_run` / `ok` / `error` |
| `last_sync_time` | Время последнего прогона (успешного или упавшего); `null`, если синхронизация ещё не запускалась |
| `last_changed_at` | Курсор `changed_at`, с которого продолжится следующий опрос Events Provider |

## Идемпотентность регистрации

Ключ идемпотентности передаётся **полем `idempotency_key` в теле запроса**
`POST /api/tickets` (не заголовком). Поле опционально, максимальная длина — 255 символов.

### Поведение

| Ситуация | Результат |
|---|---|
| Ключ не передан | Запрос обрабатывается как новый. Повторный вызов создаст ещё один билет |
| Ключ передан впервые | Обычная регистрация: вызов Events Provider, сохранение билета, запись в outbox. Ответ `201`. Пара «ключ → результат» сохраняется |
| Ключ уже использован, данные запроса те же | `201` с тем же `ticket_id`. Events Provider **не вызывается**, новый билет не создаётся, новая запись в outbox не добавляется |
| Ключ уже использован, данные запроса другие | `409 Conflict`. Билет не создаётся, сохранённый результат не перезаписывается |
| Events Provider вернул ошибку | Результат по ключу не сохраняется. Повторный запрос с тем же ключом обрабатывается как новый |

### Как определяется совпадение данных

При первой обработке от тела запроса (без самого `idempotency_key`) считается
SHA-256: поля сериализуются в JSON с сортировкой ключей, чтобы хеш не зависел от их
порядка. Хеш сохраняется вместе с ключом и `ticket_id` в таблице `idempotency_keys`.

При повторном запросе хеш пересчитывается и сравнивается с сохранённым: совпал —
возвращается сохранённый `ticket_id`, не совпал — `409`.

Ключи глобальны: пространство имён одно на всех клиентов, привязки к пользователю нет,
так как сервис не аутентифицирует запросы.

## Доставка уведомлений (Transactional Outbox)

Уведомление о покупке билета не входит в критический путь регистрации: клиент получает
`201` независимо от доступности Capashino.

1. При успешной регистрации в таблицу `outbox` пишется запись о событии
   `ticket.purchased` — **в той же транзакции**, что билет и ключ идемпотентности.
   Либо сохраняется всё, либо ничего.
2. Outbox-воркер периодически выбирает записи со статусом `pending` (FIFO по
   `created_at`, партиальный индекс по этому статусу) и отправляет их в Capashino
   через `POST /api/notifications`.
3. Запись помечается `sent` только после успешного ответа. Транзакция коммитится
   после каждой записи отдельно, поэтому сбой на одной не откатывает уже
   доставленные.
4. При ошибке доставки счётчик `attempts` увеличивается, статус остаётся `pending`,
   и запись обрабатывается на следующих итерациях. После `OUTBOX_MAX_ATTEMPTS`
   попыток запись переводится в `failed` и больше не выбирается.

### Гарантии

Доставка — **at-least-once**: между успешной отправкой в Capashino и фиксацией статуса
в БД есть окно, в котором падение процесса приведёт к повторной отправке. Поэтому в
каждый запрос передаётся `idempotency_key`, равный `id` записи outbox — он стабилен
между попытками, и Capashino дедуплицирует повторы на своей стороне. Ответ `409` от
Capashino трактуется как успех: уведомление уже существует.

## Мониторинг ошибок

Необработанные исключения автоматически отправляются в GlitchTip через `sentry-sdk`
с интеграцией FastAPI. DSN берётся из `SENTRY_DSN`; если переменная не задана, SDK не
инициализируется и сервис работает без отправки ошибок.

Уровни логирования в outbox-воркере выбраны с учётом этого: неудачная попытка с
последующим ретраем пишется как `WARNING` и инцидент не создаёт, исчерпание попыток —
как `ERROR` и попадает в GlitchTip.
